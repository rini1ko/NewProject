# 0008. Running Spry's core on Google Cloud

Status: accepted · Date: 2026-11-19

## Context
Spry runs on AWS (Lab 4-7). Lab 9 asks what it would take to run the same system on Google Cloud, and what it
would cost. Constraints: a student budget (about $0 when nobody uses the app), no long-lived credentials,
and the AWS deployment must keep working. No Google Cloud billing account could be opened for this project
(account verification refused), so the configuration is written and validated but could not be applied:
the app is proven on Cloud Run's conditions locally (docker compose, plain HTTP on `PORT=8080`).

## Decision: one row per service
| Spry on AWS | On Google Cloud | Decision | Why |
|---|---|---|---|
| S3 + CloudFront + WAF | Firebase Hosting | **replace** | CDN and HTTPS included, free plan; Cloud Storage alone gives no HTTPS on a custom domain |
| Lambda + function URL | Cloud Run | **replace** | Same container, no Lambda adapter (`Dockerfile.cloudrun`), scales to zero |
| ECR | Artifact Registry | **replace** | 0.5 GB free |
| Aurora Serverless v2 | Cloud SQL, db-f1-micro | **replace** | keeps SQL, migrations and the data layer unchanged |
| Cognito + Google | Identity Platform | **keep Cognito** | moving sign-in changes the frontend and token checks; not needed for the core |
| EventBridge, SQS, S3 events, SES | Cloud Scheduler, Pub/Sub, Eventarc | **keep on AWS** | the weekly report is a separate pipeline; Google has no email service (SendGrid or SES would be needed anyway) |
| Bedrock | Vertex AI (Gemini, Claude) | **keep on AWS** | the agenda parser runs outside the API's data path; moving it only changes the model call |
| Secrets Manager / SSM | Secret Manager | **replace** (for the moved part) | holds the generated DB password and `DATABASE_URL` |
| CloudWatch Logs | Cloud Logging | **replace** | automatic for Cloud Run |
| IAM roles, OIDC for HCP | Service accounts, Workload Identity Federation | **replace** | the API runs as its own service account; no keys are created or downloaded |
| Terraform aws provider | Terraform google provider | **replace** | separate configuration `gcp/` and separate state |

### The three questions
**The database.** Cloud SQL `db-f1-micro`, PostgreSQL 16, because Spry is relational (users, meetings, agendas, JSONB)
and Firestore would mean rewriting the data layer and the migrations. It does **not pause**: it bills about
$7.67 a month for compute plus $1.70 for 10 GB SSD even when idle. The configuration has a `db_running` switch
(activation policy `NEVER`) to stop the compute; storage still bills. Keeping Aurora and calling it across clouds was rejected:
the database would be in the private VPC of the other cloud, every request would pay cross-cloud latency (tens of ms)
and egress, and two clouds would depend on one database.
**E-mail.** Spry's email is the weekly report, which stays on AWS with SES, so there is no new key. If it moved,
SendGrid or Mailgun, with the API key in Secret Manager and read by the Cloud Run service account only.
**Not moved:** sign-in (Cognito), the weekly report and the agenda parser. They work, they are not the core, and each
is a stretch goal.

## Alternatives considered
- **Firestore instead of Cloud SQL** ($0 idle). Rejected: not SQL, so the migrations and the data access are rewritten,
  and the bill follows the number of document reads.
- **Keep the database on AWS.** Rejected, see above.
- **GKE or Compute Engine instead of Cloud Run.** More control but a cluster or a VM that bills while idle.

## Consequences
- Moved without changes: the application code and the migrations (the same image, different `CMD`).
  Rewritten: the Dockerfile (no Lambda adapter), the connection string (a Unix socket to Cloud SQL), the infrastructure.
  Lock-in is in the managed services around the compute (Cloud SQL connector, Secret Manager, Firebase rewrites), not in the code.
- Cost: about $9.40 a month idle with the instance running, $1.70 with it stopped, against about $0.30 on AWS: the database
  line decides. See docs/lab9-submission.md for four traffic profiles.
- Secrets: the DB password is generated by Terraform and stored in Secret Manager; it is also in the Terraform state, so the HCP workspace must be protected.
- No Google credentials are stored anywhere (laptop: your own login through `gcloud`; CI: Workload Identity Federation, not set up here).
- If Cloud Run or Cloud SQL is down the AWS deployment is unaffected (separate stacks).
